# 剧情资料待确认事项

## A. 用户设计决定

1. 结局锚点：建议保留“Emily 试图取代另一个自己”的主题冲突，不强制复刻具体过程。
2. 主线自由度：是否允许玩家提前离开住宅、拒绝调查、隐瞒信息？建议允许部分拒绝，但提供合理替代推进。
3. 角色永久离场：第一版建议避免不可逆淘汰，防止分支量失控。
4. 关系系统：建议先区分信任、坦诚、冲突、承诺压力，不使用单一好感度。
5. 现实数量：建议保持不确定性，不显示全局副本列表。
6. 手机：是否承载联系人、消息、照片、备忘录、通知？属于原创扩展。
7. 玩家认知界面：建议区分观察、听闻、阅读、推断和已被推翻判断。
8. 结局数量：建议先设计 3–5 个结构性方向，再决定细节。

## B. 电影事实待逐镜头复核

- 人物每次离开/返回的准确顺序。
- 荧光棒颜色、绷带、照片、盒子、便条出现时机。
- 结尾 Emily、Kevin、戒指、来电的镜头顺序。
- office、basement、patio、卫生间是画面出现还是仅对白提及。
- 二手解析中的副本编号存在解释差异，不作为官方设定。

## C. 技术适配问题

WorkBuddy 只读检查当前代码并回答：
1. EventManager 当前支持哪些 trigger/effect？
2. dialogue.json 的事实 ID、requires、grants 如何映射？
3. NPCManager 是否有稳定 instance ID？
4. SaveManager 是否保存事件唯一性、物品状态、NPC 记忆/关系？
5. CognitionManager 是否区分 observation、hearsay、inference 和 confidence？
6. 场景/现实切换是否保留 NPC 个人经历？
7. 现有数据是否支持分支条件和条件化对话？
8. 最小兼容扩展是什么？哪些需求应暂缓？

## D. WorkBuddy 第一轮任务边界

只读本目录与源码，产出 `docs/narrative/IMPLEMENTATION_MAPPING.md`：
- 字段映射；
- 可直接使用的现有系统；
- 缺失能力；
- 存档兼容风险；
- 最小扩展建议。

用户确认前，不写剧情 JSON、不改运行时代码、不删旧数据、不推送其他分支。
