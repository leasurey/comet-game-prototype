## 零、必须先说明的两项限制

### 0.1 关于电影证据

本规划**没有逐帧核对电影截图或时间码**。我依据的是《Coherence》(2013) 的公开剧情结构、
场景清单、人物动线与对白要点，以及此前已归档的 `docs/SCENE_ARCHAEOLOGY_PARTY_HOUSE.md`。

这意味着：本文件中标为 **A** 的内容，含义是「电影中确实出现过该空间或该物品，
且其功能明确」，**不代表**「我知道它在平面图上的位置、朝向和尺寸」。

电影从未提供户型图。**所有房间的长宽、相邻关系、门的位置，本质上是 C 或 D 级。**
任何把本文件平面图当作「电影官方户型」使用的做法都是错误的。

### 0.2 关于尺寸与通行能力

本文件所有尺寸均为**设计值**，未在 Godot 中实测。已实测的只有以下三项：

| 已实测项 | 数值 | 来源 |
| --- | --- | --- |
| 玩家移动速度 | 2.6 m/s | `PlayerController.DEFAULT_MOVE_SPEED` |
| 玩家胶囊 | 半径 0.32 / 总高 1.72 | `scenes/main.tscn` |
| 观察高度 | 1.62 m | `Camera3D` local y |

「某房间能容下 8 人」「某通道能容两人交错」这类判断，是按面积和人体尺度**推算**的，
不是跑出来的。第 8 节把这类结论全部列为待验证项。

**走廊占了 46.8 m²，是全屋最大的单个区域，比客厅还大。** 这是一个明确的分配失误：
3.6 m 深的贯通走廊没有任何功能，纯粹是面积浪费。

### 1.3 三处必须纠正的空间定义冲突

这三条不是设计偏好问题，是**当前实现内部自相矛盾**，会直接污染后续所有建模。

#### 冲突一：两栋房子的前门朝向相反

- `party_house` 内：前门在 **+Z 边**（z = 4.5），出生点 z = 3.4，位于前门内侧
- `house_exterior` 内：房屋占 **z 1.6 ~ 6.8**，门廊在 z ≈ 0.55（即房屋的 **-Z 侧**）

玩家在 `party_house` 里面朝 +Z 走出前门，出来本应站在房子的 +Z 侧；
但 `house_exterior` 里房子 +Z 侧是后墙外的空地。**门与实际建筑对不上。**

#### 冲突二：从自己家出门，进「另一栋房子」却回到自己家

```
party_house --前门--> house_exterior --ExitToPartyHouse--> party_house
```

`ExitToPartyHouse` 的叙事定位是「另一栋几乎一样的房子」，但它的目标就是 `party_house` 本身。
玩家从自己家出去，绕到「另一栋房子」门口进去，会**回到完全相同的室内**。
这在灰盒阶段可以当作占位，但它与「平行现实的另一栋房子」这一核心设定直接冲突，
必须在新地图里重新定义。

#### 冲突三：`living_room` 与 `party_house` 的客厅重复定义

`living_room` 是第一阶段留下的独立客厅（28 个网格节点），`party_house` 里也有一个客厅。
两个客厅互不相关，玩家无法同时存在于两者之间。`living_room` 目前只能从
`house_exterior` 的 `DoorToInterior` 进入——而那扇门在叙事上应该是 `party_house` 的前门。

**结论：新地图必须明确「一栋房子只有一个室内场景」。**

### 1.4 由此得出的第一条架构决策

> **取消「每个房间一个场景」的做法，改为「一栋建筑 = 一个场景，房间是场景内的空间分区」。**

依据：
1. 现有 `party_house` 已经是这个模式（13×9 一整个场景，房间靠内墙分隔），并且实测可跑
2. `Variant_` 变体机制按节点工作，天然适配「同一场景内切换现实」
3. 若每个房间一个场景，跨房间移动就要走 `SceneManager`，会打断第一人称连续性，
   与「无缝现实切换」的要求直接冲突

这条决策意味着：`living_room` 应当在新地图中**被 `party_house` 取代并停用**，而不是保留。

## 四、交付物 3：精确尺寸表

### 4.1 尺寸修订的推导（回应 16×11 与 13×9 两个旧方案）

**先说结论：两个都不能用。**

#### 为什么 13×9 不够

| 问题 | 具体数字 |
| --- | --- |
| 走廊面积失控 | 3.6 m 深 × 13.0 m 宽 = **46.8 m²**，占全屋 40%，比客厅大 |
| 餐厅容不下 8 座 + 拉椅 | 8 座长桌 2.6×1.05，两侧各需 0.8 m 拉椅空间、各需 0.9 m 通行 → 最小净空 **4.4 × 4.45**，现有餐厅仅 3.9×5.2，短边差 0.5 m |
| 客厅撑不住 7 NPC | 27.0 m² 容 8 人站立交谈（人均 3.4 m²）尚可，但 NPC **自主走动**时人均需 ≥4.5 m²，否则频繁互相阻挡 |
| 门洞偏窄 | 现有 1.0 m，NPC 导航时 navmesh 按 agent radius 内缩，可导航带仅约 0.3 m |

#### 为什么 16×11 过大

- 可用功能区（客厅+餐厅+厨房+走廊+玄关+卫生间+书房）实测需求合计约 **103 m² 净**
- 16×11 = 176 m²，净约 165 m²，会多出 **60 m² 没有功能归属**
- 填满它只能靠增加卧室或第二个客厅，两者都是编造
- 玩家以 2.6 m/s 横穿 16 m 需 6.2 秒，室内节奏偏拖

#### 反推推荐值

功能区净面积需求：

| 区域 | 净面积 | 推导 |
| --- | --- | --- |
| 客厅 | 33.0 | 8 人站立交谈 + 沙发组 + 7 NPC 游走，人均 ≥4 m² |
| 餐厅 | 26.4 | 8 座长桌 2.6×1.05 + 双侧拉椅 1.6 + 双侧通行 1.8 = 4.4×4.45，取 4.4×6.0 留出通往厨房的横向动线 |
| 厨房 | 23.4 | L 型台面总长 5.4 + 岛台 1.8×0.9 + 2 人操作 + 通行 |
| 玄关 | 5.3 | 2.4×2.2，容 3 人同时进出换鞋 |
| 走廊 | 2.4 | 2.4×1.0 短走廊（替代原 46.8 m² 贯通走廊） |
| 书房 | 12.5 | 3.9×3.2，电脑桌 1.6 深 0.8 + 椅后 0.9 通行 |
| 卫生间 | 5.8 | 1.8×3.2 |
| 主卧门区+侧门区 | 18.2 | 5.7×3.2，含一扇封死的门与一条通侧院的通道 |
| **合计** | **127.0** | |

加内墙（0.12 厚）约 4%，外墙（0.2 厚）周长约 47.6 m 折算 9.5 m²：

```
内净需求 127.0 + 内墙 ~5.0 = 132.0
外轮廓 = 13.8+0.4 × 9.2+0.4 = 14.2 × 9.6 = 136.3 m²
```

> **推荐房屋外轮廓：14.2 × 9.6 m = 136.3 m²，内部净 13.8 × 9.2 m = 127.0 m²**

对比：比 13×9 增加 16.3 m²（+14%），比 16×11 减少 39.7 m²（−23%）。
增加的部分全部用于「让 7 个 NPC 能走动」和「让 8 座餐桌能拉开椅子」，没有空闲房间。

## 五、交付物 4：玩家探索路线图

### 5.1 硬性要求：不得是线性路线

本设计通过**三个闭环**保证玩家不被单向锁死：

```
闭环 A（室内环）  玄关 → 走廊 → 客厅 → 餐厅 → 厨房 → 走廊 → 玄关
闭环 B（室内外环） 客厅 → 露台 → 侧院 → 前院 → 门廊 → 玄关
闭环 C（街区环）   前院 → 车道 → 街道（左/右）→ 黑暗区域 / 街对面住宅
```

**闭环 B 的意义**：玩家不必原路返回。从客厅出露台、绕侧院、经前院回到前门，
全程在室外完成，这条路径在电影对应的空间逻辑里成立（郊区单层住宅的侧院通道）。

### 6.5 NPC 与现实状态的绑定

同一 NPC 在不同现实中可以有不同位置与状态，但**不做独立场景**：

- NPC 的 `position` 由现实 id 查表得到（数据驱动，类似 `spawn`）
- NPC 的「是否在场」由现实状态决定（例如某现实里某人已经离开）
- NPC 的对话内容按现实分支

这要求 NPC 状态能够被存档序列化。**当前存档格式不含 NPC 字段**，
未来需要扩展存档 schema——这会触及「不改存档格式」的既有约束，须另行审批。

## 七、交付物 6：平行现实地图架构

### 7.1 核心原则

> **地图几何只有一份。现实不是另一张地图，而是同一张地图上的状态差异。**

这是本规划最重要的架构约束，理由：

1. 现有 `Variant_<world_id>` 机制已经按此设计，且实测可用
2. 复制整张地图意味着每次现实切换都要重新加载场景，必然打断第一人称连续性
3. 内容成本：3 个现实 × 完整地图 = 3 倍建模量，且难以保证「玩家仍能认出这是同一栋房子」

### 7.2 分区：固定 / 可变 / 触发

| 分区类型 | 内容 | 说明 |
| --- | --- | --- |
| **永久固定（Shared）** | 墙体、地板、天花板、门框、楼梯、固定橱柜、窗户位置、房屋外轮廓、街道走向、车道 | 任何现实下都不变。这是玩家「认得这是同一栋房子」的锚点 |
| **现实可变（Variant_）** | 灯光亮灭、桌面物品、照片与画、椅子位置、门开闭状态、窗户是否透光、车辆位置、街对面窗是否亮 | 通过 `Variant_<world_id>` 节点切换 |
| **切换触发区** | 黑暗区域（进入与离开）、露台（彗星事件）、街道 | 用 `Area3D` + 事件系统 |
| **统一参照物（锚点）** | 前门门牌号、餐桌、壁炉、车道上的车、街对面那栋房 | **在所有现实中必须存在且位置不变**，否则玩家会失去空间感 |

### 7.3 建议的现实数量：3 个

现有 2 个（alpha / beta）。建议扩展为 **3 个**，标为待确认：

| 现实 | 定位 | 差异强度 |
| --- | --- | --- |
| `world_alpha` | 原初。聚会正常进行，灯全亮 | 基准 |
| `world_beta` | 第一次错位。门廊灯与路灯熄灭，物品移位，出现碎玻璃 | 中 |
| `world_gamma` | 更深错位。除上述外，NPC 位置整体变化、部分家具消失、街对面房屋窗户全黑 | 强 |

**为什么不是 2 个**：电影的核心体验是「越走越远，回不去了」。两个现实只能表达一次跳变，
无法表达「这次比上次更不对」。三个现实能形成递进。

**为什么不是 5 个以上**：每增加一个现实，所有可变节点的变体数量线性增长。
3 个是内容成本与叙事效果的平衡点。

### 7.4 无缝切换的技术路径（不实施，仅规划）

```
玩家进入触发区 Area3D
   ↓
EventManager 判定转移规则（判定与执行分离，现有机制）
   ↓
WorldManager.apply_transition() 记录变更历史
   ↓
GameLocation.apply_world(new_id) 切换 Variant_ 节点可见性
   ↓
玩家节点、相机朝向、物理位置 —— 全程不动
   ↓
灯光在 0.4~0.8 秒内渐变（避免瞬间跳变被察觉成「加载」）
```

关键点：**场景不重新加载，玩家节点不重建**。这是「无缝」的技术定义。
现有 `SceneManager` 在切换地点时会 `_release_current()` 并重新实例化，
所以**现实切换绝不能走 `SceneManager`**，必须走 `WorldManager` 这条独立路径。
现有代码已经是这样，继续保持。

### 7.5 各区域的现实版本需求

| 区域 | 需要几套变体 | 备注 |
| --- | --- | --- |
| 室内主空间（客厅/餐厅/厨房） | 3 | 灯光、桌面物品、椅子、照片 |
| 走廊与南翼 | 3 | 灯光、`door to nowhere` 的门是否开着 |
| 露台 | 3 | 灯光、有无人在 |
| 前院/车道/门廊 | 3 | 门廊灯、车的位置、碎玻璃 |
| 街道 | 2 | 路灯亮灭（gamma 与 beta 共用「全黑」） |
| 黑暗区域 | 1 | **所有现实共用同一份**，它是过渡带，不是某个现实的属地 |
| 街对面住宅 | 3 | 窗是否亮、外立面细节 |

### 8.5 必须提前知道的三个工程事实

**① 项目当前没有导航系统。** 全文无 `NavigationRegion3D`。NPC 阶段必须新增，
且 navmesh 烘焙依赖碰撞体形状——如果墙体碰撞体是逐段 Box（当前就是），
烘焙出的 navmesh 在墙缝处可能出现漏缝，需要 `NavigationMesh` 的
`agent_radius` 与 `cell_size` 配合调整。**这是 NPC 阶段最大的技术风险，未验证。**

**② Compatibility 渲染器是前向渲染，灯数直接决定帧率。** 实测数据：
`party_house` 室内 12 盏灯 → 33–38 fps；室外 → 60 fps。
新房屋客厅/餐厅/厨房总面积比现有更大，若灯数继续增加，帧率会进一步下降。
**建议每套现实的室内同时点亮的灯不超过 8 盏**，其余用自发光材质替代。

**③ 现有存档 schema 不含 NPC 与坐标。** 若 NPC 位置需要按现实区分并存档，
必须扩展存档格式——这与既有「不改存档格式」约束冲突，须单独审批。
