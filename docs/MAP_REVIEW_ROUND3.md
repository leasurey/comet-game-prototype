### 1.3 上一轮 0.51 的成因

上一轮把 W0 洞口面积**当成了「误差」**，而不是单独归类。

$$0.5040\ (\text{上轮洞口，} 4.2 \times 0.12) \approx 0.51$$

数值吻合。**结论：0.51 不是计算失误，是分类缺失——门洞洞口应单独列为「未归属区域」。**

本轮补齐该类别后，等式精确成立，无需修改任何原始坐标。

## 三、门洞与导航参数

### 3.1 四个参数，四个不同用途

| # | 参数 | 作用阶段 | 本项目现状 |
| --- | --- | --- | --- |
| 1 | `NavigationMesh.agent_radius` | **烘焙时**，把可走面从碰撞体边缘向内缩 | **不存在**（项目无任何 NavigationRegion3D）**[代码]** |
| 2 | `NavigationAgent3D.radius` | **运行时**，与其他 agent 互相避让 | **不存在** **[代码]** |
| 3 | NPC 物理碰撞胶囊 | 物理阻挡 | **不存在**（无 NPC）**[代码]** |
| 4 | 玩家胶囊 | 物理阻挡 | **r = 0.32，h = 1.72** **[代码]** `scenes/main.tscn` |

**已知唯一确定的物理量：玩家胶囊半径 0.32，直径 0.64。**

NPC 胶囊 r = 0.30（直径 0.60）为 **[设计值]**，尚未实现。

### 3.2 导航网格有效宽度的计算条件

```
navmesh 有效可走宽 = 门洞净宽 − 2 × agent_radius
```

**成立条件**（缺一不可）：
1. 门洞两侧墙体碰撞体连续、无缝隙
2. `cell_size` ≤ 门洞净宽 / 10（1.2 m 门洞需 cell_size ≤ 0.12）
3. 门洞处无 `NavigationObstacle3D`
4. 门框碰撞体不凸出墙面

**第 1 条在本项目有真实风险**：现有墙体是逐段 Box **[代码]**，段间接缝可能被烘焙识别为断点。

### 3.3 「可走宽」≠「可通行」

**这是本轮要强调的边界**：navmesh 上的有效带宽度，只说明 agent 的**寻路中心线**可以经过，不代表物理上能通过。

物理通过需同时满足：

| 条件 | 不等式 |
| --- | --- |
| 物理通过 | NPC 直径 0.60 ≤ 门洞净宽 |
| 寻路可达 | 门洞净宽 − 2×0.35 ≥ 0.10（不退化） |
| 不贴墙抖动 | 有效带 ≥ NPC 直径 |

对 1.2 m 门洞：有效带 0.50 < NPC 直径 0.60 → **会出现「导航认为能过，物理上持续贴墙抖动」**。这是最隐蔽的故障模式。

### 3.4 五种通行情形的理论分析

设 agent_radius = 0.35、NPC 直径 0.60、玩家直径 0.64 **[理论推算]**

| 情形 | 所需净宽 | 1.0 m | 1.2 m | 1.6 m | 2.0 m |
| --- | --- | --- | --- | --- | --- |
| A. Emily 单独 | 0.64 + 0.10 = **0.74** | ✅ | ✅ | ✅ | ✅ |
| B. NPC ↔ Emily 交错 | 0.60+0.64+0.10 = **1.34** | ❌ | ❌ | ✅ | ✅ |
| C. 两 NPC 迎面 | 0.60+0.60+0.10 = **1.30** | ❌ | ❌ | ✅ | ✅ |
| D. 多 NPC 门口聚集 | ≥ **1.80** | ❌ | ❌ | ⚠️ | ✅ |
| E. 玩家停留 + NPC 通过 | 0.64+0.60+0.30 = **1.54** | ❌ | ❌ | ⚠️ | ✅ |

### 3.5 结论

| 用途 | 建议净宽 | 理由 |
| --- | --- | --- |
| **卫生间、书房门** | **1.20 m** | 单人使用，不会出现 B/C 情形。有效带 0.50 虽小于 NPC 直径，但这两个房间 NPC 极少进入 |
| **玄关→主空间洞口** | **1.60 m** | 8 人聚会必经，需支持 B/C 情形 |
| **前门** | **1.60 m** | 同上，且是室内外唯一通道 |
| **侧门** | **1.20 m** | 使用频率低 |
| **厨房南北连通** | **3.00 m** | 无门，开放洞口 |

**是否需要局部扩大？** 需要一处：
**玄关本身 2.4 m 宽，但两侧是墙；若聚会时 8 人集中在玄关，1.6 m 洞口仍会堵。**
建议：**玄关不设门**，与主空间完全开放（取消 W0 在 x -1.14~3.38 段的墙），洞口变为 4.52 m。

代价：内墙减少 (4.52-1.60)×0.12 = 0.35 m²，可忽略。收益：消除全屋唯一瓶颈。

## 四、跨场景坐标与朝向连续性规则

### 4.1 现状（[代码] 核实）

| 项 | 现状 |
| --- | --- |
| 场景坐标系 | 每个地点场景是**独立 Node3D**，各自原点独立 |
| 玩家出生点 | `locations.json` 的 `spawn.position`，地点本地坐标 |
| `party_house` 前门 | `FRONT_DOOR = (0, 0, 4.5)`，+Z 边 |
| `house_exterior` 门廊 | z ≈ 0.55，房屋在 +Z 侧 |
| 地面高度 | 各场景独立设定，无统一基准 |
| 转换入口 | `SceneManager.enter_location()` → `get_location_spawn()` → `PlayerController.reset_to_spawn()` |
| 初始朝向 | 由 `spawn.yaw` 决定 |

**现状问题**：坐标系不统一，跨场景必须靠「各地点写一个 spawn 坐标」硬对，无法保证连续。

### 4.2 正式规则（本轮定义）

> **规则 R1：所有地点场景共用同一世界坐标系。**
>
> 原点固定在街区西南角地面，+X 向东，+Z 向北（即房屋后部方向），Y 向上。
> 每个 `.tscn` 根节点不带平移，内部几何直接使用世界坐标。

**为什么不用局部坐标 + Transform 映射**：
Transform 映射要求为每对门洞维护 `inside/outside` 两个矩阵，8 个门洞就是 16 个矩阵，且一旦某个场景几何调整，矩阵全部失效。共享世界坐标系下，门洞在室内外两个场景中是**同一个坐标**，无需映射表。

> **规则 R2：玩家跨场景保留世界 Yaw，不重置。**
>
> 唯一例外：**首次进入某地点**（`has_visited == false`）时，使用该地点 `spawn.yaw`。

> **规则 R3：门洞两侧的位置必须由同一组坐标导出。**
>
> 室内落点 = 门洞中心 − 门法线 × 1.20
> 室外落点 = 门洞中心 + 门法线 × 0.60
> 其中法线指向「出门方向」。
