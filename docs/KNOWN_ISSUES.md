## 二、实现层面的已知限制

### 0. 变体缺失时静默回退（实测确认，尚未处理）

**实测结果**：对一个地点调用 `apply_world("world_does_not_exist")` 时，
`house_exterior` 场景没有 `Variant_default` 节点，于是回退到列表中的第一个变体
`Variant_world_alpha`，呈现内容与 alpha 世界一致，**且没有任何 warning**。

**为何重要**：第二阶段会有多个世界。任一世界漏配变体时，
玩家看到的是「另一个世界的房间」，而开发者不会收到任何提示——
这类缺陷极难靠肉眼发现。

**建议处理**：① 每个地点场景强制提供 `Variant_default`；
② 触发回退时输出 warning；③ 加入载入期静态检查。

### 0.1 部分装饰物没有碰撞（有意的取舍）

树冠、窗玻璃、地面碎片、门廊灯具等**装饰性物件没有碰撞体**。
原因：给它们加碰撞会让玩家被细小物件绊住（例如台阶旁厚度约 2cm 的玻璃碎片）。

树干同样没有碰撞，因此玩家可以穿过树。
这是明确的取舍而非遗漏——若后续需要，可为树干单独补圆柱碰撞体。

### 0.2 贴边移动会沿障碍物表面滑行

玩家斜向擦过家具或墙角时，`move_and_slide()` 会让角色**沿表面滑开**而不是完全停住。
这是 Godot 的标准行为，也是多数 FPS 的手感来源，不属于穿模。

实测表现：客厅沿 -Z 直行会先被电视柜挡住；若恰好贴着柜子右边缘
（玩家中心 x 与柜宽边界 x=1.2 重合），会滑到柜侧继续前进直至后墙。
**整个过程没有穿入任何碰撞体**（`player_movement_test` T12 断言了阻挡位置）。

### 0.3 存档不记录玩家坐标

`player_view` 只保存 yaw/pitch，不保存位置（任务书要求不修改存档格式）。
因此读档后玩家出现在该地点的 `spawn` 点，而不是上次站立的位置。
进入任意地点（含读档恢复）都会按该地点 spawn 重置。

### 0.4 碰撞体加入后，遮挡判定才第一次真正生效

静态碰撞体全部在 layer 1，而 `InteractionManager` 的遮挡判定也读 layer 1。
此前场景中没有任何静态碰撞体，`env_distance` 恒为 INF，等于没有遮挡判定。
现在它真正起作用了——这更正确，但也意味着：贴墙的热点若碰撞盒完全嵌入墙体内部，
理论上可能被判为遮挡。当前所有热点实测均可正常聚焦（由两项测试覆盖）。

### 1. HUD 由代码构建，编辑器内不可视化调整

**现状**：`core/ui/ui_manager.gd` 的 `_build_ui()` 在运行时创建所有控件。

**影响**：无法在 Godot 编辑器里拖拽调整 UI，改界面必须改代码重新运行才能看到。

**为何如此**：手写 `.tscn` 里的 Control anchor / offset 极易产出
「加载不报错但位置全错」的结果，因此选择了可读性优先的方案。

**化解方式**：对外 API 与信号已隔离，后续可替换为 `.tscn` 而不影响其他模块。

### 2. 修改场景必须重新生成

**现状**：`scenes/locations/*.tscn` 由 `tools/scene_builder.gd` 生成。

**影响**：直接编辑 `.tscn` 会在下次运行构建脚本时被覆盖。

**正确做法**：改 `tools/scene_content.gd`，然后执行

```bash
godot --headless --script res://tools/scene_builder.gd
```

### 3. 返回栈只增不减（轻微）

**现状**：`SceneManager._visit_stack` 在每次 `enter_location(remember=true)` 时压入上一个地点。
若玩家始终通过点击出口（而非「返回」按钮）移动，栈会累积。

**影响**：连续大量 `go_to` 会让栈变长，但**不影响正确性**——`go_back()` 仍是后进先出，
实测连续 4 轮往返状态正常。仅带来极轻微的内存增长。

**后续**：可加 `max_size` 上限截断。

### 4. 存档只有一个槽位

**现状**：固定写入 `user://comet_save.json`，无多存档管理。

**影响**：「保存」会直接覆盖上一次进度，无二次确认。

### 5. 「重新开始」无二次确认

**现状**：点击后立刻删除存档并开新局。

**影响**：误点将无法找回进度。建议在下一版加入确认对话。

### 6. 热点悬停反馈偏弱

**现状**：悬停时仅轻微的暖色自发光，幅度为 `emission = ±(1.0,0.88,0.62) * 0.22`。

**影响**：在较暗场景中可能难以察觉。这与任务书「热点不要过度突出」的要求做了取舍，
偏向克制的一侧。

**已知缺陷**：`Hotspot._apply_emission()` 在节点已有 `material_override` 时直接改该材质，
而 scene 内容里的材质是多个 Mesh 共享的同一实例——理论上可能出现「高亮一个，同材质其他物体跟着变」的情况。
当前热点外壳材质均为各自独立创建的 `material_override`，尚未观察到该问题，但这是一处设计隐患。

### 7. 无音效

第一阶段完全没有音频。悬疑类题材对声音依赖较高，下一阶段应优先补。

### 8. 未做导出测试

**现状**：只在编辑器/命令行下运行验证过，**尚未导出为独立可执行文件**。

**影响**：导出后的资源路径、icon、窗口配置是否正常工作未知。

### 9. 未做性能压测

场景面数与材质数量较低，理论上低端机可运行，但没有帧率数据支撑。

### 10. 存档为明文 JSON

包含地点 id、世界 id、事件历史。当前无敏感信息，但若后续加入玩家输入内容需注意。

## 三、环境相关的注意事项

### Godot 4.4+ 的 `.uid` 文件必须提交

Godot 4.4 起为每个脚本生成 `.uid` 文件用于资源标识。
**这些文件不应被 `.gitignore` 排除**，否则他人克隆后 UID 可能不一致。

本仓库已正确配置：忽略 `.godot/`，保留 `*.uid`。

### 本项目位于中文路径下

`D:\新建文件夹\comet-game-prototype` 已验证可正常构建与运行。
但某些老旧工具链对非 ASCII 路径敏感，若将来导出遇到问题，这是首要排查项。

### Godot 版本锁定

代码针对 **4.7.2-stable** 编写并验证。

已知一处版本敏感点：`Environment` 的属性名在 4.7 中是 **`ambient_light_source`**，
早期版本写作 `ambient_source`，直接跨版本复用会静默失效。
务必使用 4.7.x，或先核对属性名。
